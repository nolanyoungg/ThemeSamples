Developers / A small set of good primitives

Understand the pieces.
Build the possibilities.

Workspace, context, run, and checkpoint. A deliberately small vocabulary for a more useful kind of agent application.

Quickstart / Conceptual API

A considered
first run.

Create a workspace with the files your task needs. Describe the outcome. Decide which actions should wait for review.

These examples illustrate a fictional SDK. There is no package to install or API endpoint to call. Copy them as a product design reference.

Try the local run demo ↗ 
const workspace = await waypoint.workspace({
  name: "a-good-start",
  context: ["brief.md", "references/"],
});

const run = await workspace.run({
  task: "Turn the research into a clear brief.",
  approval: "before_write",
});
Illustrative SDK · Not an installable package

Four pieces.
A clear mental model.

Keep each responsibility understandable. A small surface is easier to inspect, adapt, and trust.

01 / WORKSPACE

A place for the work.

A named boundary containing files, task history, and the outputs worth keeping. Create one for a project or a focused working session.

workspace.create({ name, context })
02 / CONTEXT

A relevant starting point.

A scoped set of instructions and references. Keep inputs deliberate: an agent should know which material is current and which is background.

workspace.context.add(files)
03 / RUN

A task with an outcome.

An instruction, a tool boundary, and a trace of the steps taken. A finished run leaves something inspectable in the workspace.

workspace.run({ task, approval })
04 / CHECKPOINT

A moment for a person.

A pause before a consequential action. Show the proposed change, the reason for it, and a clear way to continue or revise.

run.review({ decision })

Design for the whole run

The happy path
is only the beginning.

Useful agent experiences make uncertainty visible. Think about how someone understands a pause, reviews a proposal, and returns to unfinished work.

  • queued → running → review → complete

    Give each state a clear meaning in the interface. “Working” should not hide a request for human input.

  • checkpoint.resume()

    Keep the context needed to continue. A retry should preserve useful progress and make repeated actions explicit.

  • run.artifacts()

    Show the files and conclusions a task produced, alongside the evidence needed to inspect them.

A few practical
starting principles.

SCOPE FIRST

Begin with less access.

Give each task the smallest set of files and tools that can support its outcome. Make new access a visible decision.

MAKE IT INSPECTABLE

Keep useful traces.

Explain what happened in terms a person can review. Prefer a short, meaningful run history over an unstructured stream of logs.

DESIGN THE RETURN

Leave a good next step.

A completed task should make its result obvious. An incomplete one should explain what is needed to continue.
